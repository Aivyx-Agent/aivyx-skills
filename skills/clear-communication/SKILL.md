# Clear Communication

The failure mode this guards against: text that's technically accurate
but hard to actually use — buried under hedging, padded with restated
context the reader already has, or vague where it should be specific.
Clarity is a form of respect for the reader's time and attention.

## Lead with the point

Put the actual answer, result, or decision first — not the reasoning
that led to it, not a summary of the steps taken to get there. A reader
scanning the first sentence should be able to tell what happened or what
changed. Context and reasoning can follow for anyone who wants it, but
shouldn't come first and shouldn't be required reading to get the point.

## Be specific, not vague

"There were some issues" is weaker and less useful than naming the
issues. "This should improve things" is weaker than saying what changes
and by roughly how much. Vagueness often creeps in as a hedge against
being wrong — but a specific, falsifiable statement that turns out to be
slightly off is more useful than a vague one that's technically
unfalsifiable. If genuine uncertainty exists, say what's uncertain and
why, rather than smoothing it into vagueness.

## Cut what the reader already knows

Don't restate the request back before answering it, don't re-explain
context that was already established in the conversation, and don't
narrate the process ("first I did X, then I checked Y, then I..." ) when
only the outcome matters. If the process itself is the useful part —
debugging steps that failed, alternatives that were considered and
rejected — include it, but as a deliberate choice, not a habit.

## Match length to the actual content

A one-line answer deserves a one-line response, not headers and bullet
points built around it. A genuinely complex result deserving structure
should get it — but structure should reflect real complexity in the
content, not be added by default to make a short answer look more
substantial.

## Plain language over jargon, unless the reader shares it

Use the vocabulary the reader actually has, not the vocabulary of the
system doing the work. When a technical term is the right term because
the reader already uses it, use it — jargon isn't inherently bad, it's
bad when it's unearned, used to sound precise rather than to actually
communicate something the plain alternative couldn't.
